# Vanta 2 Architecture Contract (Batches 3 + 4)

This document records the interfaces and behavior present in the combined workspace on 2026-10-21. It is a contract for future work, not a guarantee that Android runtime behavior or remote database migrations have been validated. The Room and Supabase migration audits and build blocker are tracked separately.

## Ownership and mutation rules

- A signed-in Vanta user owns task occurrences, habit occurrences, review notes, focus history, sync checkpoints, and queued mutations. Room queries and local outboxes must always include the owner ID.
- Supabase is canonical for server task and occurrence data. Room is the device's local-first projection and write queue; it may show user data offline.
- Google Calendar is a separately authorized, read-only source. Its cache is separate from Vanta occurrence tables and is keyed by Vanta owner plus an opaque Google account key.
- User preferences are device/app behavior settings in DataStore, not account credentials. Do not put Supabase auth tokens, Google OAuth tokens, or API secrets in them.
- Pure planner and analytics projections do not own persistence. Only repository / store APIs may mutate records or queue remote writes.
- Additive changes to persisted fields require coordinated Room and Supabase migrations, bootstrap/delta mapping, and offline mutation serialization. Do not edit already applied Supabase migrations.

## Model and interface contract

| Interface | Ownership and source of truth | Offline and sync behavior | Invariants and mutation authority |
|---|---|---|---|
| **Task** | The canonical task definition is the owner-scoped Supabase tasks row. Android has no separate Room Task entity; CachedOccurrence.taskId links the local occurrence projection to it. | Quick Capture may create locally through a typed PendingMutation; normal sync replay creates/updates the server task and reconciles local IDs. Existing task creation payloads remain compatible. | A task's default schedule type and priority provide defaults for generated occurrences. Task data is mutated through the repository's typed task operations or the authorized server/MCP RPCs, never by planner projections. |
| **Occurrence** | Supabase task_occurrences is canonical remotely. Room cached_occurrences is the active local projection; completed records are copied to occurrence_history before cache pruning. Rows carry userId, taskId, status, schedule and constraint fields. | Completion uses the idempotent pending_completions queue; create/reschedule uses pending_mutations. Local optimistic state remains available offline and replays for its owner. | scheduledFor is a placement start, not a deadline. A deadline is completion constraint metadata. Completion, skip, and reschedule are distinct state changes. Repository APIs own writes. |
| **Habit** | A habit is a task/occurrence with kind = "habit"; there is no duplicate Room Habit entity. Habit history comes from the same occurrence_history records used elsewhere. | Completion uses the occurrence completion queue. Explicit skip has its own idempotent, user-scoped pending_habit_skips outbox. | Streaks count recorded expected occurrences: completed extends, a past pending occurrence breaks, skipped is neutral, and today's pending occurrence remains open. Do not synthesize missing recurrence dates. The displayed history is bounded to 365 days. Only habit occurrences may be skipped through review. |
| **FocusSession** | The existing Focus Mode FocusSession is the source for active/finished session state. Active session state is persisted locally in SharedPreferences under a hashed user key; completed/ended history is stored in Room focus_session_history. | Focus history is local and does not sync to Supabase. Offline focus use remains available. Offline-created occurrence ID reconciliation is owner-scoped. | Finishing Focus Mode does not itself complete an occurrence. Task completion follows the normal occurrence path. Analytics measures elapsed session time, not attention or device activity. Only FocusSessionStore and the repository's history method may write these records. |
| **PendingMutation** | Room pending_mutations is a durable, ordered, owner-scoped intent queue. Completion and habit skip have separate queues and retain their own idempotency semantics. | The repository replays queued operations when connectivity/auth permits, with retry state. A mutation must never be replayed under a different user. | Keep the operation type and typed payload fields consistent with the local optimistic row and remote RPC. Do not edit queue rows from UI or projection code. The repository is the mutation authority. |
| **ScheduleType** | The shared enum is in planner/PlannerModels.kt; Room and Supabase persist the string values HARD, SOFT, and FLEXIBLE. | Existing scheduled rows backfill as SOFT; unscheduled rows backfill as FLEXIBLE. Schedule fields are copied through bootstrap, delta, and typed queued writes. | HARD is fixed for drag/automatic proposals. SOFT has a current placement that may be moved. FLEXIBLE has no start and is eligible for planning. A successful move of FLEXIBLE becomes SOFT. An explicit manual reschedule may move a HARD item while retaining its HARD type; do not move HARD silently or through automatic planning. |
| **ScheduleBlock** | A pure display/planning projection. Vanta blocks derive from owner-scoped Room occurrences; Google blocks derive from the separate owner-scoped Calendar cache. | Vanta block edits go through the occurrence mutation queue. Google blocks are read-only and never enter task mutations, MCP, or AI as raw event records. | editable is limited to pending, future SOFT Vanta blocks. All-day events expand to the selected planning-zone day bounds. Keep source, priority, deadline, and window metadata when constructing or suggesting a move. |
| **DaySchedule** | A pure projection built by buildDaySchedule from bounded occurrence rows, a planning window, and optional Calendar blocks. No persisted DaySchedule exists. | Rebuilt from Room on updates; disconnected Calendar is represented by an empty block list. | Planning bounds must have positive length. Completed IDs remain informational/read-only. Week rendering may omit unbounded flexible tasks from each daily view because the tray presents them once. The planner must not infer a start from a deadline. |
| **Conflict** | ScheduleConflict is deterministic derived state from planner blocks and constraints. It is not persisted. | Recomputed from the latest local schedule before presenting alternatives or applying a proposal. | Conflicts are review prompts, not mutations. HARD blocks and Calendar commitments are not auto-moved. Proposals require current-state validation before writes. |
| **CandidateSlot** | A deterministic, pure planner output from free intervals, duration, priority and placement constraints. It is not persisted. | Candidate calculation is available offline. | Each slot must fit its duration, planning bounds, earliest/latest window, deadline, busy intervals, and other placements. AI output is untrusted and must pass the same local validation. |
| **MorningBriefing** | A local, transient projection from today's cached occurrences. It is not a remote model or separately persisted record. | Works offline; Calendar data is not required. | Scheduled count and first item derive from the local day. Planned minutes appear only when every timed item has a valid duration. Habit count is by distinct habit task. High-priority task count is omitted if priority is unavailable; priority is passed from CachedOccurrence. |
| **DailyReview** | Room daily_reviews is keyed by (userId, reviewDate); Supabase daily_reviews is the remote owner-scoped copy. | Note and finished marker save locally first and sync via the user-derived review RPC. Notes are optional and limited to 4,000 characters. | UI must not supply the owner identity to the server RPC. “Keep” is a review decision only; it is not a durable scheduling mutation. Move/reschedule and habit skip use their existing queues. Repository owns save/sync. |
| **Analytics** | A local projection over bounded occurrence_history and existing focus_session_history; no third-party analytics store is used. | Available offline after history exists locally. Queries use the selected 7- or 30-day range; habit history uses up to 365 days. | Planned time comes from stored task durations; actual time comes from finished Focus Mode sessions. Only matching task occurrences contribute estimation samples. Do not send cross-user aggregates or create a second focus history. |
| **UserPreferences** | Typed UserPreferences in DataStore via UserPreferencesRepository. This is device/app configuration, separate from account identity and auth stores. | Preferences work offline. Task-reminder enablement is synchronized for the current device token; other display/planning settings remain local. | Validate/normalize values on read/write. The stable API is the typed Flow and repository update/reset methods. Reset touches preferences only. No OAuth or service secrets belong here. |
| **Delta Sync checkpoint** | Room sync_checkpoints stores SyncCheckpoint(userId, revision, bootstrapped); the remote ordered change log/revision is authoritative for server changes. | Checkpoint is local per user. Bootstrap stages owner rows, then delta replay advances the checkpoint after successful local application. | Never share checkpoints across accounts, skip revisions, or advance before applying changes. Outbox replay and delta application must preserve occurrence identity reconciliation and scheduling fields. |
| **Widget state** | WidgetOccurrenceSnapshot is computed by a bounded Room query from the current owner's occurrences and completion state. It is not a separate persisted domain model. | Updated from local state, including queued offline completion/reschedule changes; widget refresh is requested by repository actions and the existing refresh worker. | Keep counts and planned minutes owner-scoped and derived from the same occurrence semantics as Today. Widget code may read projections; it does not own task mutations. |

## Cross-feature behavior

- **Today and Week:** Both use the shared schedule models and user planning preferences. Week observes one bounded Room range and a separate bounded Calendar range. Today remains functional with no Calendar connection.
- **Quick Capture and drag/reschedule:** Quick Capture consumes the default-duration preference and writes through the repository. Timeline drag is restricted to pending, timed SOFT tasks. Explicit date-picker reschedule uses the same repository queue and retains scheduling metadata.
- **Morning briefing and Calendar:** Briefing depends on generic local occurrence data, not Google APIs. Calendar cache availability does not determine whether the briefing can render.
- **AI Plan My Day:** The server obtains authenticated owner data; Android supplies an ephemeral access token per request. AI proposal is preview-only until local validation against a fresh schedule and explicit apply. Missing service configuration should make only AI planning unavailable.
- **Offline and account changes:** Visible Room flows switch by owner ID; queued writes and history remain owner-tagged. Sign-out refuses to discard unresolved completion/task mutations, drains focus reconciliation, then clears active occurrence cache and sync checkpoint. Feature state in the UI must be reset or keyed by account.

## Date and timezone policy

Task-day, planner, habit, history, briefing, analytics, and widget calculations currently use Asia/Kolkata through several constants/helpers. Treat that as the current canonical Vanta data-day zone; do not introduce a second task-day zone without a deliberate migration and UI decision. Notification wall-clock scheduling uses the device's system timezone, which is a separate policy. Calendar expansion must receive the same task/planning zone used by the surface.

## Startup and optional integrations

- Calendar has no compile-time dependency in briefing or planner domain models. Calendar cache is separate and read-only.
- `VantaRoot` holds the Calendar repository in a lazy holder and opens it only once an authenticated owner is available. Signed-in Today and Week still observe the local cache so previously connected Calendar blocks can appear after restart.
- `AiPlanClient` is also held lazily. Its Ktor `HttpClient` is created only after an explicit planning request and is closed with the root lifecycle if initialized.
- These repositories do not issue network requests during construction. Calendar refresh is freshness-gated and runs only for the signed-in owner; AI network access follows a user action.

## Change checklist for Batch 5+

Before adding a persisted concept or changing a shared interface:

1. Reuse the owner-scoped source of truth above; do not create parallel task, habit, focus, analytics, preferences, or schedule models.
2. Identify local-first behavior, queue type, and server counterpart before writing UI.
3. Update Room entity, migration, bootstrap, delta mapper, mutation serializer/replay, and tests together for persisted occurrence fields.
4. Keep Calendar and AI optional; raw OAuth credentials and service secrets must never enter Room, task mutations, MCP, or model prompts.
5. Revalidate automatic and AI proposals against latest owner-scoped state before applying.
6. Preserve bounded database reads and lazy UI rendering.
7. Document any invariant change here before implementation.
